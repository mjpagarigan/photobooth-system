# Ticket — QR download page image fails to load (ARCHIVE UNAVAILABLE)

Label: wayfinder:research
Status: closed

## Question

Why does the QR download page (`apps/public`, `/photo#<token>`) show the retryable
error state "WE COULD NOT OPEN THIS PHOTO / We could not load this photo right now."
with a TRY AGAIN button when a guest scans the QR code, and what is the fix?

## Resolution

The screenshot's state is the **retryable** branch of `App.tsx` (token parsed OK,
page-origin gate passed), so the failure happens inside `resolvePhoto()` or
`fetchPhotoImage()` (`apps/public/src/api.ts`). Root cause is a **three-layer
deployment coherence failure** around the new R2 303-redirect serving path — any
single layer mismatch reproduces the exact symptom, and all three are currently
misaligned:

1. **Stale frontend vs. new function (primary).** The Edge Function
   (`supabase/functions/photo/index.ts:163-209`) answers `POST /photo/image` with
   **303 See Other** to a presigned R2 URL when `storage_backend = 'r2'`. The
   *committed* frontend (`api.ts`) sends `fetch(..., { redirect: 'error' })` — a 303
   throws TypeError → caught → retryable error → infinite TRY AGAIN. The fix
   (`redirect: 'follow'` + R2-origin check) exists only as **uncommitted** working-tree
   changes. Deployed frontend built from HEAD + deployed function serving R2 = guaranteed
   failure.
2. **R2 bucket CORS is doc-only, never provisioned.** With `redirect: 'follow'`, the
   browser follows the 303 cross-origin to
   `https://<bucket>.<account>.r2.cloudflarestorage.com/...`. The bucket CORS policy
   (exact page origin, GET/HEAD, expose Content-Type/Content-Length) exists only in
   `docs/SECURITY_AND_RETENTION.md:79-95` — nothing in the repo applies it. Missing CORS
   → redirected fetch fails → same retryable error.
3. **Build-time R2 origin + CSP must match exactly.** `fetchPhotoBlob`
   (`api.ts:101-106`) requires the final response origin to equal build-time
   `VITE_PUBLIC_R2_ORIGIN` exactly (virtual-hosted style:
   `bucket.account.r2.cloudflarestorage.com`), and `index.html` CSP `connect-src` is
   templated with the R2 origin (`vite.config.ts`). A build with stale/missing env or a
   stale CSP blocks the fetch → same retryable error.

Also ruled out by the screenshot: 404/expiry (would render the *non-retryable*
"This photo is unavailable or has expired." without TRY AGAIN) and token/origin-gate
failure (same non-retryable path).

Fix direction: deploy frontend and functions from the same working tree (commit the
R2-redirect frontend changes), apply the pending Supabase migrations
(`20260824*` — `resolve_photo_session` must return `storage_backend`), configure the R2
bucket CORS policy from the doc, set `VITE_PUBLIC_R2_ORIGIN` at build, and verify the
full chain with a hosted smoke test.

## Key facts from recon

- QR encodes `https://<PUBLIC_PAGE_ORIGIN>/photo#<43-char-base64url token>`
  (`apps/kiosk/src/main/cloud/qr-service.ts:11-21`).
- All photo API calls are POST with token in JSON body; `image` route returns either
  200 streamed JPEG (supabase backend) or 303 → presigned R2 GET (r2 backend)
  (`supabase/functions/photo/index.ts`).
- Frontend validates: response origin, `content-type: image/jpeg`, content-length,
  JPEG magic bytes FFD8FF…FFD9 (`api.ts:89-138`).
- `apps/public/public/_headers` was deleted in the working tree; CSP/_redirects now
  generated by `vite.config.ts` per build.
- LAN/offline delivery (`apps/kiosk/src/main/server/offline-delivery-server.ts`) is a
  separate, independent implementation — unaffected.
